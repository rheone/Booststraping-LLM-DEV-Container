# Culture-specific formatting

Every `CsvReader`/`CsvWriter` constructor requires a `CultureInfo` (directly, or via a
`CsvConfiguration` that carries one) because number, date, and separator parsing/formatting are all
culture-dependent operations — there is no locale-agnostic default CsvHelper can safely assume.

## Choosing a culture

- **`CultureInfo.InvariantCulture`** — the right default for machine-generated or machine-consumed
  files: exports/imports between systems, log-adjacent data, anything not directly read by a person
  in a specific locale. Numbers use `.` as the decimal separator; dates round-trip predictably
  regardless of what locale the process happens to run under.
- **A specific named culture (`new CultureInfo("de-DE")`)** — required when the file's actual
  content uses that locale's conventions: a comma decimal separator, day-first dates, or
  locale-specific text a person in that region produced or will read directly (e.g. an accountant's
  spreadsheet export).
- **Never `CultureInfo.CurrentCulture` implicitly** — passing nothing and letting a default apply
  makes the read/write behavior depend on the running machine's OS locale settings, so a file that
  parses correctly in development can fail or silently misparse in a different deployment
  environment. Always pass an explicit culture.

```csharp
var config = new CsvConfiguration(new CultureInfo("de-DE"))
{
    Delimiter = ";", // common pairing with de-DE, whose decimal separator is a comma
};
```

## Per-member format strings

`Map(...).TypeConverterOption.Format(...)` overrides the format used for one member, independent of
the reader/writer's overall culture — use this when most of a file follows one convention but a
specific column has its own fixed format (e.g. an always-ISO-8601 timestamp column in an otherwise
locale-specific file).

```csharp
Map(o => o.PlacedAt).TypeConverterOption.Format("yyyy-MM-dd");
```

## Number styles

`TypeConverterOption.NumberStyles(...)` controls what `System.Globalization.NumberStyles` a numeric
member accepts — for example, allowing a leading currency symbol or thousands separators that the
default numeric parsing would otherwise reject as bad data.

```csharp
Map(o => o.Total).TypeConverterOption.NumberStyles(NumberStyles.Currency);
```

## Reading files with an unknown or mixed culture

A file whose culture isn't known ahead of time (uploaded by an external party, historically
generated by more than one system) needs detection or normalization before it reaches CsvHelper —
CsvHelper itself does not attempt to auto-detect a culture from the file's content. Sniff the
delimiter and decimal-separator convention from a sample of the file, or require the uploader to
declare it, rather than trying several `CultureInfo` values against the whole file and picking
whichever one parses without error.
